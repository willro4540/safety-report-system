시설 안전 민원 신고 프로그램 v2 — MySQL 실연동 + 신고/감사이력 스키마 재구축

v1(초기 버전)은 데이터베이스(MySQL) 연결 코드가 일부러 막혀있는 상태였습니다. db/connection.py가 항상 예외를 던지도록 되어 있어서, 신고 접수/조회/처리 전부 로컬 JSON 파일로만 동작했습니다. 이번 글은 그 목업(가짜 동작)을 걷어내고, 실제 MySQL에 신고가 저장되고 관리자 처리 이력까지 남는 구조로 바꾼 과정을 처음부터 끝까지 다룹니다. 프로그래밍을 몰라도 순서대로 따라오면 똑같이 만들 수 있게 썼습니다.

이 글을 다 따라 하면: 로컬 JSON 파일에만 의존하던 신고 프로그램이, 진짜 MySQL 데이터베이스에 신고를 저장하고 관리자가 언제/누구에게 어떤 처분을 내렸는지까지 별도 표로 남기는 구조로 바뀝니다.

0. 용어 사전 (처음 나올 때 한글 발음도 같이)

  • 스키마(schema, 스키마) — 데이터베이스에 어떤 표(테이블)와 어떤 칸(컬럼)이 있는지 미리 정해둔 설계도
  • 목업(mock, 목) — 실제 기능 대신 가짜로 동작을 흉내내는 구현. 비용/자원 없이 개발 가능하게 해줌
  • ENUM(이넘) — 컬럼에 들어올 수 있는 값을 미리 정한 목록으로만 제한하는 MySQL 컬럼 타입
  • FOREIGN KEY(포린 키, 외래키) — 한 테이블의 값이 다른 테이블에 실제로 존재하는 값만 가리키도록 강제하는 제약
  • bcrypt(비크립트) — 비밀번호를 안전하게 암호화(해시)하는 방식. 결과 문자열이 항상 60자로 고정됨
  • pymysql(파이마이에스큐엘) — 파이썬 코드가 MySQL에 접속할 수 있게 해주는 라이브러리
  • EPSG / WGS84(더블유지에스84) — 전 세계 좌표계를 코드로 표준화한 체계. EPSG:4326 = WGS84 = GPS가 기본으로 쓰는 위도·경도 좌표계
  • 감사 이력(audit log, 오딧 로그) — "누가·언제·무엇을" 했는지 원본 데이터와 별도 표에 남기는 기록
기억할 한 문장: 코드 안에 SQL 문장이 적혀 있다고 실제로 DB에 저장되는 게 아니다 — 연결(connection)이 진짜로 되어 있어야 그 SQL이 비로소 실행된다.

1. 왜 패치가 아니라 다시 짜야 했는가 — 코드를 열어보고 찾은 문제

v1 코드를 처음부터 다시 읽어보니, DB가 막혀있다는 것 말고도 실제로 여러 군데가 어긋나 있었습니다. 이 문제들을 먼저 정리하지 않으면 MySQL을 살려도 제대로 동작하지 않았을 겁니다.

  • 신고 접수 코드에 DB 저장 시도 자체가 없었음 — ui/report.py는 로컬 JSON에만 썼고, MySQL을 살려도 신고는 여전히 DB에 안 들어감
  • 관리자 처리 코드도 DB 갱신 없음 — 상태 변경/기각 처리가 항상 로컬 JSON만 고쳤음
  • 테이블 이름이 이미 어긋나 있었음 — SQL 문은 complaints를 쓰는데, 파일명·변수명은 전부 report 계열
  • DB 조회 컬럼이 로컬 JSON보다 적었음 — 신고 유형, 사진 경로, 기각 사유가 DB SELECT 문에는 빠져있었음
  • 회원가입 코드가 권한(role) 컬럼을 안 채움 — signup.py의 INSERT에 role이 없었음

즉 SMS 알림 기능(관리자가 상태를 바꾸면 신고자에게 문자 발송)이 제대로 작동하려면, 회원·신고 데이터를 다루는 방식 전체를 다시 설계해야 했습니다.

2. MySQL에 실제 테이블 만들기 (schema.sql)

먼저 데이터베이스 자체를 설계도(스키마)대로 만듭니다. users(회원), reports(신고, 기존 complaints에서 이름 통일), admin_actions (관리자 처리 감사 이력) 3개 표를 만듭니다.

⚡ 원문 통짜 보기 (숙련자용, 절차 생략하고 바로 치기)

mysql -u root -p < db/schema.sql
mysql -u root -p safety_report

🔧 db/schema.sql 전체 코드 (심화)

이 파일이 왜 이렇게 생겼는지: VARCHAR(60)은 bcrypt 해시가 항상 60자이기 때문에 고정한 것이고, role/status를 ENUM으로 제한한 건 "말이 안 되는 값"(예: 상태에 오타)이 아예 저장되지 못하게 DB 차원에서 막는 것입니다. FOREIGN KEY는 존재하지 않는 회원 ID로 신고가 등록되는 것을 DB가 스스로 거부하게 만듭니다.

CREATE DATABASE IF NOT EXISTS safety_report
    CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

USE safety_report;

-- 회원(신고자/관리자 공통)
CREATE TABLE users (
    user_id     VARCHAR(20)  PRIMARY KEY,
    password    VARCHAR(60)  NOT NULL,   -- bcrypt 해시 고정 길이(60자)
    name        VARCHAR(50)  NOT NULL,
    phone       VARCHAR(20)  NOT NULL,
    role        ENUM('user','admin') NOT NULL DEFAULT 'user',
    created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB CHARACTER SET utf8mb4;

-- 민원 신고 (구 SQL의 complaints → reports로 통일)
CREATE TABLE reports (
    id             INT AUTO_INCREMENT PRIMARY KEY,
    user_id        VARCHAR(20)  NOT NULL,
    type           VARCHAR(30)  NOT NULL,
    location       VARCHAR(255) NOT NULL,   -- 사람이 읽는 주소/설명 텍스트
    latitude       DOUBLE       NULL,       -- EPSG:4326(WGS84), GPS EXIF 원본값 그대로
    longitude      DOUBLE       NULL,       -- EPSG:4326(WGS84)
    content        TEXT         NOT NULL,
    image_path     VARCHAR(255) NULL,
    status         ENUM('접수','처리중','완료','기각') NOT NULL DEFAULT '접수',
    reject_reason  TEXT         NULL,
    created_at     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(user_id)
) ENGINE=InnoDB CHARACTER SET utf8mb4;

-- 관리자 처리 이력 (감사 로그)
CREATE TABLE admin_actions (
    id           INT AUTO_INCREMENT PRIMARY KEY,
    report_id    INT          NOT NULL,
    admin_id     VARCHAR(20)  NOT NULL,
    action       ENUM('완료처리','기각') NOT NULL,
    reason       TEXT         NULL,
    created_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (report_id) REFERENCES reports(id),
    FOREIGN KEY (admin_id)  REFERENCES users(user_id)
) ENGINE=InnoDB CHARACTER SET utf8mb4;

4. db/connection.py — 가짜 연결 걷어내기

기존 get_connection()은 무조건 예외를 던져서 DB 연결을 강제로 실패시켰습니다. 그 아래에 이미 진짜 연결 코드가 주석('''...''')으로 준비되어 있었길래, 그 함수를 그대로 살리고 가짜 예외를 지웠습니다.

def get_connection():
    return pymysql.connect(
        host = os.getenv("DB_HOST", "localhost"),
        user = os.getenv("DB_USER", "root"),
        password = os.getenv("DB_PASSWORD", ""),
        database = os.getenv("DB_NAME", "safety_report"),
        charset = "utf8mb4"
    )

.env가 없거나 MySQL이 안 떠 있으면 이 함수 호출 자체가 예외를 던지는데, 다른 파일들의 try/except 구조가 그 예외를 잡아서 자동으로 로컬 JSON 모드로 전환하도록 이미 짜여 있었습니다 — 그래서 이 한 곳만 고쳐도 나머지가 그대로 작동합니다.

5. ui/report.py — 위도·경도를 별도 칸에 저장하기

비유: 기존 코드는 주소록 한 칸에 "홍길동010-1234-5678"을 통째로 적어놓은 것과 같았습니다. 사진에서 GPS를 뽑으면 "위도: 35.123456, 경도: 126.789012" 라는 문자열 하나로만 저장됐는데, 지도 기능은 문자열이 아니라 숫자를 요구합니다. 그래서 GPS를 추출하는 순간 위도·경도를 별도 변수로도 붙잡아 두게 고쳤습니다.

1. __init__에 좌표를 담을 변수 2개를 추가한다:

self.latitude = None
self.longitude = None

2. extract_gps()에서 좌표를 계산하자마자 그 변수에 저장한다:

self.latitude = lat
self.longitude = lon

→ 화면에는 여전히 "위도: .., 경도: .." 문자열이 보이지만, 내부적으로는 숫자도 따로 저장된 상태.

3. 신고 접수 시 로컬 JSON 대신 새로 만든 save_report()를 호출하도록 바꾼다:

self.save_report(report_type, location, content)

4. DB 저장을 먼저 시도하고, 실패하면 로컬 JSON으로 자동 전환하는 함수를 새로 만든다:

def save_report(self, report_type, location, content):
    try:
        from db.connection import get_connection
        conn = get_connection()
        cursor = conn.cursor()
        cursor.execute(
            "INSERT INTO reports (user_id, type, location, latitude, longitude, content, image_path) "
            "VALUES (%s,%s,%s,%s,%s,%s,%s)",
            (self.user_id, report_type, location, self.latitude, self.longitude,
             content, self.image_path or "")
        )
        conn.commit()
        conn.close()
    except Exception:
        self.save_local(report_type, location, content)

→ MySQL이 살아있으면 reports 표에 한 줄이 새로 생긴다. DB가 없으면 기존처럼 local_reports.json에 저장된다.

6. ui/admin.py — 관리자 처리 감사 이력 남기기 (가장 큰 변경)

비유: 기존 코드는 도서관에서 책장 A(DB 목록)를 보고 "3번째 책"을 골랐는데, 실제로 빼내는 건 책장 B(로컬 JSON 파일)의 3번째 책이었던 것과 같은 상태였습니다. 두 책장의 순서가 우연히 같을 때만 문제가 안 드러났습니다.

정의: 원래 화면 목록은 DB가 연결되면 DB 데이터를 보여주는데, "상태 변경"/"기각" 버튼을 누르면 항상 로컬 JSON 파일만 수정했습니다. DB가 연결된 상태에서는 화면에 보이는 신고와 실제로 바뀌는 데이터가 서로 다른 신고일 수 있었던 것입니다.

1. 목록을 불러올 때, DB든 로컬이든 결과를 같은 모양의 딕셔너리 리스트로 통일해서 저장한다 (self.current_rows), 그리고 어느 쪽을 썼는지도 기록한다 (self.data_source):

self.data_source = "db"
for row in rows:
    self.current_rows.append({
        "id": row[0], "user_id": row[1], "type": row[2],
        "location": row[3], "content": row[4], "status": row[5],
        "reject_reason": row[6], "created_at": row[7]
    })

→ (DB 실패 시) self.data_source = "local"로 바뀌고 로컬 JSON에서 같은 모양으로 채워진다.

2. 선택한 항목을 텍스트 파싱 대신, 화면 목록의 실제 선택 위치로 바로 꺼낸다:

def get_selected_row(self):
    idx = self.list_widget.currentRow()
    if idx < 0 or idx >= len(self.current_rows):
        QMessageBox.warning(self, "선택 오류", "신고 항목을 선택하세요.")
        return None
    return self.current_rows[idx]

→ 기존처럼 화면 텍스트의 대괄호 숫자를 다시 읽어서 해석하는 방식보다 훨씬 안전해진다.

3. 상태를 바꿀 때, 목록을 읽었던 곳과 똑같은 곳에 쓰도록 함수 하나로 통일한다:

def _update_status(self, row, new_status, reason=None):
    action = "완료처리" if new_status == "완료" else ("기각" if new_status == "기각" else None)

    if self.data_source == "db":
        try:
            from db.connection import get_connection
            conn = get_connection()
            cursor = conn.cursor()
            if reason is not None:
                cursor.execute(
                    "UPDATE reports SET status = %s, reject_reason = %s WHERE id = %s",
                    (new_status, reason, row["id"])
                )
            else:
                cursor.execute(
                    "UPDATE reports SET status = %s WHERE id = %s",
                    (new_status, row["id"])
                )
            if action:
                cursor.execute(
                    "INSERT INTO admin_actions (report_id, admin_id, action, reason) VALUES (%s,%s,%s,%s)",
                    (row["id"], self.admin_id, action, reason)
                )
            conn.commit()
            conn.close()
            return
        except Exception:
            pass  # DB 갱신 실패 시 로컬로 폴백

    if not os.path.exists(LOCAL_REPORTS):
        return
    with open(LOCAL_REPORTS, "r", encoding="utf-8") as f:
        reports = json.load(f)
    reports[row["id"]]["status"] = new_status
    if reason is not None:
        reports[row["id"]]["reject_reason"] = reason

🔧 get_user_phone()도 DB부터 조회하게 바꾸기 (심화)

SMS 발송 시 전화번호를 조회하는 get_user_phone()도 원래는 로컬 JSON만 봤습니다. 이제 users 표가 실제로 있으니, DB부터 먼저 확인하도록 바꿉니다:

def get_user_phone(user_id):
    try:
        from db.connection import get_connection
        conn = get_connection()
        cursor = conn.cursor()
        cursor.execute("SELECT phone FROM users WHERE user_id = %s", (user_id,))
        row = cursor.fetchone()
        conn.close()
        if row:
            return row[0]
    except Exception:
        pass

    if not os.path.exists(LOCAL_USERS):
        return None
    with open(LOCAL_USERS, "r", encoding="utf-8") as f:
        users = json.load(f)
    for u in users:
        if u.get("user_id") == user_id:
            return u.get("phone")
    return None

→ 새로 가입하는 회원은 항상 role='user'로 명확히 저장된다(이전엔 이 값이 안 채워져서 DB 기본값에만 의존했음).

3. ui/login.py에서 관리자로 로그인했을 때, 로그인한 user_id를 AdminWindow에 넘겨준다:

self.main_window = AdminWindow(user_id)

→ 이제 관리자 패널이 "누가 로그인했는지"를 알고 있어서, 감사 이력에 정확한 admin_id가 남는다.

⚡ 원문 통짜 보기 (숙련자용, 절차 생략하고 바로 치기)

1. (bash 프롬프트, 프로젝트 폴더 안에서) 기존 SMS 브랜치를 기준으로 새 브랜치를 만든다:

→ Switched to a new branch 'feature/v2-mysql-map' 메시지가 뜬다.

2. 바뀐 파일들을 스테이징한다:

→ 아무 글자도 안 뜨면 정상.

3. 커밋한다:

이번 커밋은 원칙(직접 타이핑)의 예외로 Claude가 대신 작성했습니다 — 왜 예외가 됐는지는 safety_report_study_procedure.md 17번 항목에 그대로 남겨뒀습니다. 다음 변경부터는 다시 직접 타이핑하는 방식으로 돌아갑니다.
