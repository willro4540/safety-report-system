# Git 완전 처음부터 이해하기 — 비개발자를 위한 커밋/푸시/브랜치 정리

이 글은 프로그래밍을 전혀 몰라도, 영어를 몰라도 이해할 수 있도록 쓴 글입니다.
나중에 Git을 다 잊어버린 상태에서 이 글 하나만 다시 읽어도 처음부터 감을 잡을 수 있게
만들었습니다. 실제로 제가(개발자 겸 이 글을 쓴 사람이) 오늘 겪었던 실수 사례도 그대로
넣었으니, "이론"이 아니라 "실전에서 왜 위험한지"까지 같이 이해하시면 됩니다.

## 0. 시작하기 전에 — Git이 뭔지 한 문장으로

**Git(깃)**은 "내가 작업한 파일의 변경 기록을 시간순으로 저장해두는 프로그램"입니다.
한글로 굳이 발음하면 "깃"이라고 읽습니다(사람 이름 아니고, "get(얻다)"과 발음만 비슷한
그냥 고유명사예요).

**GitHub(깃허브, 발음: 깃-허브)**는 그 기록을 인터넷에 올려서 나 혼자만이 아니라
다른 사람과 같이 보고 공유할 수 있게 해주는 웹사이트입니다.

**비유로 이해하기**: Git은 "여러 번 저장할 수 있는 타임캡슐"이고, GitHub은 "그 타임캡슐들을
모아두는 공용 창고"입니다. 창고에 넣기 전까지는(=푸시하기 전까지는) 그 타임캡슐이 내 방
안에만 있는 거고, 아무도 못 봅니다.

## 0-1. 우분투(Linux)에서 만든 프로젝트를 왜 지금 윈도우에서 다루고 있나

이 안전신고 프로젝트는 개발완료보고서에 적혀있듯 원래 **우분투(Ubuntu, 리눅스 계열
운영체제)**에서 만들어졌습니다. 그런데 지금 우리는 **Windows(PowerShell)**에서 이 프로젝트의
Git 작업을 하고 있죠. 이게 헷갈릴 수 있는데, 정리하면 이렇습니다.

**좋은 소식**: `git add`, `git commit`, `git push`, `git checkout -b` 같은 **Git 명령어
자체는 Windows든 Mac이든 Linux(우분투)든 완전히 똑같습니다.** Git은 운영체제를 가리지 않고
똑같이 동작하도록 만들어진 도구예요. 그래서 이 교육자료에 나온 명령어는 어느 컴퓨터에서든
그대로 씁니다.

**다만 딱 하나, 실제로 부딪히는 차이가 있는데** — 바로 **줄바꿈 문자**입니다.

- 리눅스/우분투(원래 이 프로젝트를 만들 때 쓴 환경)는 파일의 줄바꿈을 `LF`라는 방식으로 저장
- Windows는 전통적으로 `CRLF`라는 방식으로 저장

오늘 실제로 터미널에 이런 경고가 여러 번 떴었죠:

```
warning: in the working copy of 'ui/admin.py', LF will be replaced by CRLF the next time Git touches it
```

이게 바로 "이 파일은 원래 리눅스 방식(LF)으로 저장되어 있었는데, 지금 Windows에서 건드리니까
Windows 방식(CRLF)으로 바뀔 거야"라고 Git이 미리 알려주는 안내문입니다. **에러가 아니라
그냥 정보성 경고**라서 무시하고 진행해도 대부분 문제없습니다 — 코드 내용 자체가 바뀌는 게
아니라 "줄 끝에 보이지 않는 문자 하나"가 바뀌는 것뿐이거든요.

**정리**: Git 명령어는 OS 상관없이 똑같이 쓰면 되고, 저 경고 문구는 "무서운 에러"가 아니라
"원래 리눅스에서 만든 파일이라 그렇다"는 것만 알고 넘어가면 됩니다.

## 1. 용어 사전 (처음 나올 때 한글 발음도 같이)

| 영어 | 한글 발음 | 뜻 |
|---|---|---|
| repository (repo) | 레포지토리 (줄여서 "레포") | 프로젝트 하나를 담는 "폴더 + 기록 전체" |
| commit | 커밋 | 지금 상태를 "여기까지 저장!"하고 스냅샷(사진 찍듯) 남기는 것. **내 컴퓨터 안에서만** 일어남 |
| push | 푸시 | 내 컴퓨터에 쌓인 커밋들을 GitHub(공용 창고)로 올려서 남들도 보게 하는 것 |
| pull | 풀 | 반대로, GitHub에 있는 남의 최신 변경사항을 내 컴퓨터로 받아오는 것 |
| branch | 브랜치 | "나뭇가지"라는 뜻 그대로 — 같은 프로젝트를 복사해서 별도로 이어 쓸 수 있는 "갈래" |
| merge | 머지 | 서로 다른 브랜치(갈래)에서 각자 진행한 내용을 하나로 합치는 것 |
| checkout | 체크아웃 | 지금 보고 있는/작업할 브랜치를 다른 브랜치로 바꿔서 옮겨타는 것 |
| clone | 클론 | GitHub에 있는 프로젝트 전체를 내 컴퓨터로 통째로 복사해오는 것(처음 한 번) |
| remote | 리모트 | "원격"이라는 뜻 — 내 컴퓨터가 아니라 인터넷 저편(GitHub)에 있는 저장소를 가리키는 말 |
| origin | 오리진 | 리모트 저장소(보통 GitHub)를 부르는 기본 별명. "origin에 push한다" = "GitHub에 올린다" |
| HEAD | 헤드 | "지금 내가 서 있는 위치"를 가리키는 화살표. 보통 지금 작업 중인 브랜치의 맨 끝 커밋 |
| stash | 스태시 | 아직 커밋할 준비가 안 된 작업 내용을 "잠깐 서랍에 넣어두는" 임시 보관함 |
| staging area | 스테이징 에어리어 | 커밋하기 직전에 "이번엔 이 파일들만 저장할게"라고 담아두는 장바구니 같은 공간 |
| force push | 포스 푸시 | 원래는 안 되는 걸 강제로 밀어붙여서 덮어쓰는 푸시. **매우 위험, 아래 3번 참고** |
| amend | 어멘드 | 방금 만든 커밋(스냅샷)의 내용/메시지를 다시 고쳐 쓰는 것 |
| reset --hard | 리셋 하드 | 지금까지의 작업 내용을 특정 시점으로 **완전히 되돌리고, 그 사이의 변경은 버리는** 명령 |
| LF / CRLF | 엘에프 / 씨알엘에프 | 파일에서 "줄바꿈"을 표시하는 두 가지 방식. 리눅스/Mac은 LF, Windows는 전통적으로 CRLF 사용 |

## 2. 그림으로 이해하는 4단계 흐름

Git 작업은 항상 이 4단계를 거칩니다. **이 순서를 이해하는 게 커밋/푸시 헷갈림을 없애는
핵심**입니다.

```
① 작업 폴더           ② 스테이징(장바구니)     ③ 로컬 저장소(내 컴퓨터)    ④ 원격 저장소(GitHub)
(그냥 파일 수정 중)      git add                 git commit                git push
   내 컴퓨터                내 컴퓨터                 내 컴퓨터                  인터넷
   ─────────────►         ─────────────►           ─────────────►
```

- **① → ②**: 파일을 수정한 다음 `git add 파일명`을 하면, "이번 스냅샷에 이 파일을
  포함시킬게"라고 장바구니에 담는 것.
- **② → ③**: `git commit -m "메시지"`를 하면, 장바구니에 담은 내용으로 스냅샷 하나를
  찍어서 **내 컴퓨터 안의 역사 기록**에 저장. 이 시점까지는 **아무도 못 봅니다. 나만 봄.**
- **③ → ④**: `git push`를 해야 비로소 그 스냅샷들이 GitHub로 올라가서 **팀원/다른 사람이
  볼 수 있게** 됩니다.

### 그래서 "커밋하고 또 커밋한다"는 게 무슨 뜻이냐면

**커밋은 "완전히 끝난 최종본"이 아니라 "지금까지 진행 상황의 저장 지점" 하나하나입니다.**
게임에서 세이브 포인트를 여러 번 찍는 것과 같아요. 하루에 10번 커밋해도 전혀 이상하지
않습니다 — "로그인 기능 완성", "버튼 색 수정", "오타 고침" 이렇게 작은 단위로 여러 번
커밋하는 게 오히려 정상이고 권장되는 방식입니다.

### 팀원과 협업할 때 헷갈리는 부분 정리

> "작업 중에 커밋받는 건지, 아니면 내가 저장하는 건지 헷갈린다"

이렇게 정리하면 됩니다:

- **커밋(commit) = 내가 하는 것, 내 컴퓨터에만 저장** (팀원은 아직 전혀 모름)
- **푸시(push) = 내가 하는 것, 이제 팀원도 GitHub에서 볼 수 있음**
- **풀(pull) = 내가 하는 것, 팀원이 이미 올려둔(push한) 내용을 내가 받아오는 것**
- 즉 "커밋을 받는다"는 개념 자체가 없습니다 — **커밋은 항상 내가 내 컴퓨터에 하는 것**이고,
  그걸 팀원에게 전달하려면 반드시 **push**를 해야 하고, 팀원 것을 받아오려면 **pull**을
  해야 합니다. "받는다"는 느낌이 드는 동작은 push가 아니라 **pull**입니다.

## 3. 브랜치(branch) — 평행 세계 비유

같은 문서를 여러 명이 동시에 고치면 서로 덮어써서 사고가 나겠죠. 그래서 각자 **자기만의
사본(브랜치)**을 만들어서 거기서 작업하고, 다 끝나면 원본에 합치는(merge) 방식을 씁니다.

```
master (원본, 항상 안전하게 유지)
  │
  ├── feature/로그인기능    ← A가 여기서 작업 (master는 안 건드림)
  │
  └── feature/문자알림      ← B가 여기서 작업 (master는 안 건드림)
```

- 브랜치를 새로 만드는 것(`git checkout -b 브랜치이름`)은 **master를 전혀 손상시키지
  않습니다.** 그냥 "지금 상태를 복사한 새 갈래"를 하나 더 만드는 것뿐이에요.
- 각자 브랜치에서 마음껏 커밋해도 master는 그대로 안전합니다.
- 나중에 "이 기능 다 됐다" 싶으면 master에 **합치는(merge)** 작업을 합니다.

## 4. ⚠️ 위험한 명령어 — 반드시 조심해야 할 것들

아래 명령어들은 **한 번 실행하면 되돌리기 어렵거나, 팀원의 작업을 날려버릴 수 있는**
명령어입니다. 초보일 때는 특히 조심해야 합니다.

### ⚠️ `git push --force` (포스 푸시)
- **무엇을 하나**: GitHub에 이미 올라간 기록을 "내 걸로 강제로 덮어쓰기" 합니다.
- **왜 위험한가**: 팀원이 이미 뭔가를 push해놨는데, 내가 그걸 모른 채로 force push하면
  **팀원의 커밋이 통째로 사라질 수 있습니다.**
- **안전한 상황**: 나 혼자만 쓰는 브랜치, 그것도 **아무도 아직 pull(받아가기)하지 않은
  상태**일 때만 비교적 안전합니다.
- **팀 프로젝트 규칙**: 여러 명이 같이 쓰는 브랜치(예: master, develop)에는 **절대 혼자
  판단으로 force push하지 마세요.** 반드시 팀원에게 먼저 알리고 동의를 구하세요.

### ⚠️ `git reset --hard` (리셋 하드)
- **무엇을 하나**: 아직 커밋 안 한 내 작업 내용을 **전부 버리고** 특정 시점으로 되돌립니다.
- **왜 위험한가**: "아직 저장 안 한 변경사항"은 reset --hard 한 번으로 **복구가 거의
  불가능**하게 사라집니다 (일반 문서 편집기의 "실행 취소"처럼 되돌릴 수 없어요).
- **안전하게 쓰는 법**: 실행 전에 반드시 `git status`로 "저장 안 된 변경사항이 있는지"
  확인하고, 있다면 먼저 `git stash`(잠깐 서랍에 넣기)로 안전하게 빼두세요.

### ⚠️ `git branch -D` (대문자 D, 강제 삭제)
- 소문자 `-d`는 "이미 master에 합쳐진 브랜치만" 안전하게 지워주지만, 대문자 `-D`는
  **아직 합쳐지지 않은 작업까지 강제로 삭제**합니다. 대문자 옵션을 쓸 땐 그 브랜치에
  중요한 작업이 없는지 한 번 더 확인하세요.

### ⚠️ `.git` 폴더를 직접 삭제하는 것
- `.git`이라는 숨김 폴더 안에 **모든 버전 기록 전체**가 들어있습니다. 이걸 지우면 지금까지
  쌓인 커밋 역사가 전부 사라집니다(파일 자체는 남아있어도 "기록"은 복구 불가능).

### 공통 원칙
> **"이미 GitHub에 올라갔고, 남이 봤을 수도 있는 것"을 건드리는 명령어는 항상 조심.**
> **"아직 내 컴퓨터에만 있는 것"을 건드리는 건 상대적으로 안전** (그래도 `git stash`로
> 백업해두는 습관을 들이면 더 안전합니다).

## 5. 오늘 실제로 겪었던 사례로 복습하기

오늘 이런 상황이 있었습니다 (실제 있었던 일 그대로):

1. 첫 커밋을 AI가 대신 해줘서, 커밋 기록에 "AI가 같이 만들었다"는 표시(`Co-Authored-By`)가
   남았습니다.
2. 이걸 "내 이름으로만" 남기고 싶어서, `git commit --amend`(방금 커밋 다시 쓰기)로 고쳤습니다.
3. 그런데 이 작업을 **master가 아니라 다른 브랜치(feature/sms-notifion)에서** 하는 바람에,
   원래 master는 그대로 남아있고 "고쳐진 버전"은 다른 브랜치에 따로 생겼습니다.
4. 이걸 다시 master로 옮기기 위해 `git reset --hard`(다른 브랜치의 내용으로 강제 교체)를
   썼는데, **이때 아직 커밋 안 한 다른 작업(문자 알림 기능 코드)이 같이 있어서** 자칫하면
   그 작업이 날아갈 뻔했습니다.
5. 그래서 `git stash -u`(아직 커밋 안 한 작업을 통째로 서랍에 잠깐 넣어두기)로 먼저
   안전하게 빼둔 다음에 reset을 했고, 나중에 `git stash pop`(서랍에서 다시 꺼내기)으로
   복구했습니다.
6. 거기다 사용자와 AI가 **동시에 같은 저장소에서 비슷한 명령어를 실행**하는 바람에
   "브랜치가 이미 삭제됨", "브랜치가 이미 존재함" 같은 충돌 메시지도 났습니다 — 다행히
   최종적으로는 문제없이 정리됐습니다.

**이 사례에서 배울 점**:
- `reset --hard`를 쓰기 전엔 **항상 `git status`로 저장 안 된 변경사항부터 확인**할 것.
- 저장 안 된 게 있으면 **먼저 `git stash`로 빼두고** 위험한 명령어를 실행할 것.
- 여러 사람(또는 사람+AI)이 **동시에 같은 저장소를 만지면 충돌이 난다** — 한 번에 한
  사람(또는 한 프로세스)만 작업하는 게 안전.

## 6. 자주 쓰는 명령어 치트시트

| 하고 싶은 것 | 명령어 |
|---|---|
| 지금 뭐가 바뀌었는지 확인 | `git status` |
| 파일을 장바구니에 담기 | `git add 파일명` (전체는 `git add .`) |
| 장바구니 내용으로 스냅샷 찍기 | `git commit -m "메시지"` |
| GitHub로 올리기 | `git push` |
| GitHub 최신 내용 받아오기 | `git pull` |
| 새 브랜치 만들고 옮겨타기 | `git checkout -b 브랜치이름` |
| 다른 브랜치로 옮겨타기 | `git checkout 브랜치이름` |
| 지금까지 커밋 역사 보기 | `git log --oneline` |
| 저장 안 한 작업 잠깐 넣어두기 | `git stash -u` |
| 넣어둔 작업 다시 꺼내기 | `git stash pop` |
