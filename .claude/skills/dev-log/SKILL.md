# 프로젝트 개발 로그 스킬

`학습용`의 `study-log` 스킬(Python/C# 교재 학습용)과 같은 철학을 실제 포트폴리오 프로젝트
개발 세션에 적용한 버전. 세션이 끊겨도 `safety_report_study_procedure.md`만 보면 지난
작업/결정 이유를 바로 파악할 수 있게 하는 것이 목적.

## 기록 규칙 (자동, 확인 요청 불필요)

1. 프로젝트 루트의 `safety_report_study_procedure.md`에 기록
2. 표 형식 유지: `| 단계 | 유형 | 내용 | 쉬운 설명 | 확인 결과 |`
   - 단계 번호는 파일 끝 마지막 번호 다음부터 이어서 부여
   - 유형 예시: 발견 / 분석 / 보안 점검 / 코드 작성 / 기능 추가 / 리서치 / 정책 논의 /
     Git 워크플로 논의 / 프로세스 정리
3. 새로운 영어 용어(라이브러리명, 서비스명 등)가 처음 나오면 용어 사전에 한글 발음과 함께 추가
4. 세션이 끊기면 파일 끝에 `## 다음 진행 예정` 섹션을 갱신 (체크박스 형식)

## Git 작업 권한 규칙 (2026-08-28 확정)

- **평상시 커밋/브랜치 생성은 Claude가 직접 실행해도 된다.**
- **예외: 새 포트폴리오 저장소의 "첫/founding 커밋"만은** 사용자 본인 이름으로만 남기는 것을
  선호함(공동저자 트레일러 없이) — 다른 사람이 채용 목적으로 볼 가능성이 있는 저장소의 시작
  지점이기 때문. 새 포트폴리오 레포를 만들 때는 이 점을 먼저 확인할 것.
- 이미 트레일러가 붙은 채로 push된 첫 커밋을 나중에라도 정리하고 싶어하면
  `git commit --amend` (또는 필요시 `reset --hard` + 안전한 `git stash -u` 백업)로 처리하고,
  force-push 전에는 반드시 현재 브랜치/미커밋 변경사항 상태를 `git status`로 확인한 뒤 진행한다
  (실수로 미커밋 작업을 날리지 않도록).

## 코드 타이핑 연습 (선택, 2026-08-28 사용자 요청)

- Claude가 코드를 제시했을 때, 사용자가 시간 여유가 있으면 **직접 타이핑해서 적용**하는 것도
  좋은 학습 방법으로 인정한다 (study-log 스킬의 "타이핑=필사" 개념과 동일한 효과 기대).
- 다만 이건 선택 사항이지 강제 규칙이 아니다 — 바쁘면 Claude가 바로 파일에 적용해도 된다.
  매번 사용자에게 "직접 치시겠어요?"라고 물어볼 필요는 없고, 사용자가 여유 있다고 표현하면
  그때 코드 스니펫만 깔끔하게 제시하는 방식으로 전환한다.

## Mock-우선 개발 (외부 유료/제한 API 연동 시)

- SMS, 이메일 등 실제 발송 시 비용/쿼터가 소모되는 외부 서비스는, 개발 중 기본값을
  Mock(콘솔 로그만 남김)으로 하고, 실제 호출은 `.env`의 명시적 플래그(`SMS_ENABLED` 등)로만
  켜지게 설계한다 (`sms_notifier.py` 패턴 참고).
- 서비스의 "무료 이벤트/체험 기능"을 자동화해서 대체제로 쓰는 식의 접근은 제안하지 않는다
  (서비스 약관 위반 소지) — 정식 무료 크레딧 활용 + Mock 모드 조합으로 충분히 해결한다.

## 보안 점검 습관 (2026-08-28, 실제 Gmail 앱 비밀번호 하드코딩 발견 이후 확립)

- 외부에서 가져온 기존 프로젝트를 정리해서 커밋하기 전에는, `password|smtp|gmail|secret|api_key`
  등의 키워드로 소스 전체를 grep해서 하드코딩된 시크릿이 있는지 반드시 확인한다.
- 발견되면 `.env` + `python-dotenv`로 분리하고 `.env.example`(값 비운 템플릿)만 커밋한다.
- 이미 노출된 적 있는 실제 시크릿(예: 대화 중에 값이 그대로 노출된 경우)은 폐기/재발급을
  한 번은 명확히 권장하되, 사용자가 넘어가면 반복해서 재차 권하지 않는다.
